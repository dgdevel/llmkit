# Contributing to llmkit

First off, thank you for taking the time to contribute to **llmkit**! All contributions, ideas, and bug reports are welcome.

However, before you open an Issue or a Pull Request, please read this document carefully. Understanding the project's pace and requirements will save both your time and mine.

## Project Pace & Expectations

**llmkit** is a hobby project maintained by a single developer in their spare time.

No commercial SLA: This is not commercial software. There are no guaranteed response times or delivery dates.

Pacing: Development happens when time and energy allow. It might take days, weeks, or longer to review an Issue or PR.

No bumping: Please do not post comments like "bump", "any updates?", or ask for ETAs. They create unnecessary noise and notifications. Rest assured, all open issues are read and tracked.

Respect the boundaries: Pushing for faster resolutions or demanding immediate support will result in the Issue being closed.

## Reporting Bugs

Bug reports are essential, but debugging takes time. To help me fix issues quickly, I need complete and actionable reports.

Before submitting a bug, please ensure you:

- Search existing Issues: Ensure the bug hasn't already been reported.

- Use the Bug Report Template: When you open a new issue, GitHub will provide a template. Fill out all required fields.

- Provide a Minimal Reproducible Example (MRE): I cannot fix a bug I cannot reproduce. "It doesn't work" is not a bug report. Include:

1. The exact version of llmkit you are using.

2. Your OS/Environment details.

3. Step-by-step instructions to trigger the bug.

4. Expected behavior vs. Actual behavior.

5. Relevant logs, screenshots, or error messages.

Incomplete bug reports will be closed. If an Issue lacks the necessary information to reproduce the bug, it will be tagged as needs more info. If the info is not provided within 14 days, the Issue will be automatically closed.


## Suggesting Features

I appreciate ideas for making **llmkit** better, but please remember that my time for implementing new features is very limited.

- Open a Feature Request Issue and describe the use case (what problem does it solve?), not just the solution.

- Understand that opening a feature request does not guarantee it will be implemented.

## Pull Requests (Code Contributions)

I welcome code contributions, especially for fixing bugs! However, to avoid wasting your time or mine, please follow these rules:

- Discuss first: If you are planning to fix a bug, comment on the existing Issue first to let me know you're working on it. If you want to add a new feature, you must open a Feature Request Issue and get my approval before writing code. Unsolicited Pull Requests for new features may be closed without review.
- Keep it focused: One Pull Request should address exactly one Issue. Do not mix bug fixes, refactoring, and new features in the same PR.
- Follow the style: Ensure your code matches the existing coding style and conventions used in the project.
- Test your code: Make sure the existing tests pass and add new tests if applicable.
